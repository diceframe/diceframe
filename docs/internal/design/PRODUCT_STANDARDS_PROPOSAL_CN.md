# 产品规范与长期优势：实施提案

[English](PRODUCT_STANDARDS_PROPOSAL.md) | 简体中文

状态：2026-10-15 维护者讨论稿。本文补充现状核对、格式约定与执行顺序，不等于已经新增 schema、API、市场审核能力或发布承诺。现行要求仍以[工程规则](../../ENGINEERING_RULES.md)、[架构事实](../../ARCHITECTURE_CN.md)和[已接受 ADR](../../adr/README.md)为准。下文明确区分“已有”和“建议”。

## 要建立什么优势

目标是可自行部署、可扩展、能够长期游玩的游戏平台：AI 协助创作与叙事，服务端掌握规则和状态，作者的内容能在多局游戏与不同入口复用。

建议把投入集中在三项能持续积累的资产：

1. **可信的长期战役**：升级恢复、确定性规则、多人隐私、历史与事务正确性都有证据，玩家敢投入数月。
2. **可复用的作者生态**：作者能独立完成导入、修订、验证、分发、开局；内容来源、身份、引用和兼容边界清楚。
3. **同一局跨入口与模型**：网页、手机、Bot 使用同一个权威游戏，模型可替换，断线和重连可恢复。

积累的是兼容内容、作者、战役验收样例、迁移可靠性与用户信任。用户数据可携带；不依赖限制导出、秘密提示词或默认收集私人对话。

英文提案已核对的 [Friends & Fables](https://fables.gg/)、[AI Dungeon](https://help.aidungeon.com/faq/the-memory-system) 和 [Foundry](https://foundryvtt.com/article/module-development/) 官方资料说明，AI 主持、世界资料、记忆与包元数据已经有功能重叠。因此优先投资完整流程与可验证可靠性。这是产品判断，不是竞品可靠性测试结论。

## 现有格式：已有基础，不再重造一套

以下按当前工作副本核对，不表示本地新增代码已经合并或发布。

| 对象 | 当前实现 | 如何使用 |
| --- | --- | --- |
| 安装包 | `.dfplugin`，ZIP 兼容，单个 `plugin.json` | 统一分发外壳；内容包与运行代码的插件分别判断风险 |
| 包清单 | `schema_version: 1`；Content V2 为 `content_schema_version: 2`，typed locale schema 1 | 包版本、清单版本、内容版本各有职责 |
| 冒险模组 | `plugin_type: content-pack`，`content_profile: adventure-module`，`content_delivery_mode: catalog`，声明 `adventure_packages` | 安装先登记目录，使用冒险时按需物化；缺省字段的旧包保留旧自动导入语义 |
| 冒险正文 | 独立 `manifest.json`、graph v1/v2、规则 runtime 要求 | 放章节、场景、分支、遭遇；不用为市场再定义一套冒险格式 |
| 规则内容 | Ruleset Bundle 与 runtime 自有目录验证器 | 规则内容快照/机制能力、冒险剧情和安装外壳分别负责，不混成一份万能格式 |
| 可携带对象 | World、Book、Adventure、Character 的各自格式与 ContentRef | 共享引用，不抹平各自的数据权威与生命周期 |
| 扩展能力 | type descriptor、SDK、公有服务接口 | 复用渠道、工具、Provider、Bot 扩展；`import-export` 仍是预留类型 |
| 包验证 | 共用的安装预览、安装和 CLI 深度校验 | 已能校验声明的冒险、目录与 runtime；能解析不代表实际游玩已验证 |
| 市场 | Hub 目录与仓库回退、Release 解析到 commit、权限/风险审核边界、冒险元数据投影 | 冒险发现可以沿用现有内容包市场 |

**建议：市场中的“冒险”是内容包的分类与筛选入口。** 一个包可以有多个冒险，外加世界、资料册、角色与地图。包详情列出包含的冒险，每个冒险提供开局入口。无需新增安装器或文件后缀。

“内容”与“执行能力”必须分别判断。当前共享 profile 校验已经拒绝 catalog 模式的 `entrypoint`，包括冒险模组。未使用 catalog 的旧 static 类型仍可携带入口，风险策略将其标为 `unrestricted-process`。市场展示应依据实际风险，不能把所有 `content-pack` 都标成纯数据。

世界负责场景、背景与默认关联；资料册负责按需检索的知识；冒险负责剧情图；规则 runtime 负责机制；内容包负责分发。这些对象不互相代替。

## 格式规范怎么定

以下是建议逐步落地的作者约定与准入要求，未实现的部分不能当成当前已经强制执行。

| 方面 | 建议约定 | 必须避免的混淆 |
| --- | --- | --- |
| 源文件 | 新规范数据使用 UTF-8 JSON、相对路径；示例与导出统一两空格；Markdown 写说明/正文，素材独立引用 | PDF 是导入来源，不是可执行原生模组；不为排版重写既有用户数据 |
| 身份 | 包 ID、资源 ID、冒险 ID 分别遵守现有验证器；标题、翻译不是身份 | 不给所有持久化 ID 强套新正则；同名不同来源不能相互覆盖 |
| 引用 | ContentRef 通过所属 resolver 解析来源、类型、ID 与必要 digest | Content V2 ResourceRef 与跨包 ContentRef 不是可以随意互换的字符串 |
| 版本 | 新包建议按定义好的公开契约采用 SemVer；schema/runtime 整数保持原有含义 | 提升包主版本不等于自动迁移存档；Git tag 本身不保证不可变 |
| 依赖 | 复用 `requires.rulesets` 的 `id`、整数 `minimum_version` 和冒险 runtime 要求 | runtime 契约版本不是应用版本；当前不承诺通用依赖求解、任意版本范围或自动下载 |
| 语言 | 核心界面/文档维护英语与简中；作者如实声明内容语言，可只提供一种 | 翻译不能改变规则、权限和 ID；社区译文可按维护政策暂停、回退英文 |
| 自动化 | 按实际冒险/功能标示 `reference`、`guided`、`deterministic` 并附验收范围 | 有法术介绍不等于实现法术；一个遭遇通过不等于全部规则全自动 |
| 来源与维护 | 公共上架说明维护者、联系渠道、源码、使用说明、变更记录、许可和素材署名 | 能导入不等于能公开再分发；核心维护者不自动接管无人维护的作品 |

SemVer 的 patch 用于兼容修正、minor 用于兼容新增、major 用于不兼容变化，前提是先说清该包的公开契约；见 [SemVer](https://semver.org/spec/v2.0.0.html)。建议同一版本固定对应同一份内容，修订发新版本；市场强制不可变记录仍需实现。存档继续使用它已绑定的身份、版本和 digest，不能静默追随最新版。

公共目录建议采用适用的 [SPDX 许可标识](https://spdx.org/licenses/)，不同许可的正文、图片、音频分别保留声明。许可字符串与作者自述不是权利验证。私人本地导入与公开上架采用不同准入要求；不自动给旧本地包改许可或删除内容。

当前冒险导出器已经使用的清单片段如下，仅展示外壳关系，**不是完整可安装示例**：

```json
{
  "schema_version": 1,
  "content_schema_version": 2,
  "locale_schema_version": 1,
  "plugin_type": "content-pack",
  "content_profile": "adventure-module",
  "content_delivery_mode": "catalog",
  "adventure_packages": ["adventures/lantern-harbor"]
}
```

完整包还需要身份、版本、配置 schema、资源声明和通过验证的冒险正文。不要把讨论稿里的 JSON 片段直接当新 API。

## 界面与文字排版也需要约定

复用当前 theme token 与功能组件，不为每个编辑器另建一套设计系统。建议把反复出现的界面问题转成共同行为要求：

| 场景 | 建议验收标准 |
| --- | --- |
| 表单 | 标签、输入与选择框对齐；相关说明集中到同一位置；高级项折叠但不丢值 |
| 操作按钮 | 每个任务有明确主操作；次级操作聚合；重复入口需要明确的上下文用途 |
| 卡片与筛选 | 密度、控件高度、操作对齐一致；资料册标题、世界、来源与维护状态分开表达 |
| 手机布局 | 内容可读；弹窗不偏移越界；任务区可折叠；导航不遮住输入区域 |
| 异步操作 | 等待、成功、失败可观察；按钮不可用说明原因；支持的任务能取消；AI 用量范围说清 |
| GM 排版 | 历史与流式消息都保留明确段落边界；现有首行两字符缩进作用于每段，不只作用于整块的第一行 |

不往存档文本里塞全角空格伪造缩进。叙事与状态协议分开，非可信文本转义，不能因支持排版就允许任意 HTML 执行。排版修复不改变权威正文与游戏状态。

## 插件规范：数据包与执行插件分开验收

| 轨道 | 建议验收重点 |
| --- | --- |
| 世界/资料/冒险纯数据包 | 无执行入口；引用和素材完整；runtime 真实支持；GM 信息不泄露；安装、开局、保存、重载 |
| 工具/渠道/Provider/Bot 扩展 | 生命周期、退出清理、输入/descriptor 校验、权限和 actor、超时、失败回退 |
| 主题/音色素材 | 对应类型的过滤/素材校验、来源、预览；无需套用无关冒险测试 |

插件代码通过公开服务与 SDK 扩展，不能直接把写数据库或猜内部字段当作正式接口。AI 可以提议工具调用，游戏修改仍由领域服务判断权限和执行。

**进程插件当前以宿主操作系统用户运行，不是完整 OS 沙箱。** manifest 权限、Agent 的 `read_only` 声明都不能代替系统隔离。更新增加执行入口、凭据访问或其他权限，应重新评估风险；不能因为名字还叫内容包就自动放行。保留现有权限/风险扩大的拒绝边界。

## 内容市场规范：上架、安装、更新各有责任

建议按这条用户流程落地，下面描述产品行为，不是已经新增的 API 枚举：

1. **作者提交前**：共用验证器给出阻断错误和警告，定位具体文件、资源、引用，并说明处理方法。
2. **上架审核**：核对确切版本、来源 commit、产物；分别记录格式、兼容、执行风险和游玩验收。通过格式校验不冒充“所有玩法兼容”。
3. **目录详情**：显示作者、语言、目标规则/runtime、自动化范围、包含资源、安装方式、依赖、风险与维护状态。
4. **安装结果**：预览影响；成功后明确“已安装”，给出“查看内容”“用此冒险开局”；失败给原因与重试入口，禁用按钮解释缺项。
5. **更新处理**：重新验证、比较权限、检查存档绑定。旧局按原绑定运行；无法保留其依赖时明确阻断。不要默认为最新版本，本文也不承诺已经具备通用多版本共存和包回滚仓库。
6. **停止维护/撤回**：停止维护、弃用、安全下架分开显示理由和已验证版本。无人维护但仍兼容的包可以保留；阻断后续分发不等于静默删除用户本地内容和存档。

下载后计算的 SHA-256 能标识收到的字节；没有独立可信的预期 digest 或签名，它不等于作者身份认证。commit 固定提供可追溯性，也不等于安全或游玩认证。建议后续将“审核版本、源码 commit、预期产物 digest、校验报告、审核范围”绑定为服务端记录；作者自填 `verified`、`official` 不应成为认证依据。作者签名体系需另行设计。

本仓库能证明客户端怎样消费 Hub 目录，不能单凭它断言独立部署的 Hub 已经完成上传者认证、审核和撤回全链路；实施前需核对 Hub 本体。

## 规范放哪里，谁维护

| 责任方 | 负责 | 维护边界 |
| --- | --- | --- |
| 核心仓库 | schema、验证器、runtime 能力、安装与存档契约、版本化示例 | 不再手抄第二份市场目录 |
| 插件索引仓库 | 投稿校验、维护者准入流程、已审核权限基线、索引 schema、目录同步 | 支持类型、权限和模组语义不能独立漂移 |
| 内容仓库 | 作者入门、原创/许可示例、上架指南与兼容证据 | 复用核心验证，不重写一套验证规则 |
| Hub | 发布者授权、目录状态、版本/产物/审核记录、分发决定 | 不接管游戏规则和存档权威 |
| 作者/维护者 | 内容正确性、来源许可、支持版本、插件行为、认领的翻译 | 暂停维护不自动把义务转给核心维护者 |

这次核对发现[外部插件指南](https://github.com/diceframe/diceframe-content/blob/main/docs/en/plugin-development.md)仍写旧包体积上限并把 Provider 列为预留，本地已有更大的 [package limits](../../../src/plugin_host/package_limits.py) 与支持 Provider 的 [descriptor](../../../src/plugin_host/support.py)。优先补版本匹配与示例 CI；能从常量/descriptor 生成的支持表和限制片段就生成，避免多处手抄。schema 的 `$id` 是标识，不代表对应网址已经托管。

**插件索引仓库也必须同步调整。** 核对的 [registry validator](https://github.com/diceframe/diceframe-plugins/blob/e1cc03aec1a1f55aa851991cade4908912a19d73/scripts/registry.cjs)仍拒绝 Provider 投稿与核心已有的 `ai.providers` 权限；直接运行验证器还发现，它接受 `adventure-module + legacy_autoimport`，而核心会拒绝此组合。索引已经透传完整 manifest，不能简单说“完全没有冒险元数据”；缺口在对应语义校验与真实产物验收。当前 CI 运行索引自身测试/校验，没有接入核心的深度模块校验。

建议将支持类型、实际权限策略、profile 组合和 Release 验证与明确的核心版本对齐，并保留最低应用版本要求。不能只给索引扩白名单，让旧客户端误以为也能使用新能力。用共用正反例验证“投稿、CI、安装判断一致”，全程不执行非可信插件入口；保留来源身份、已审核权限基线与风险变化后的重新审核。

文档分工保持：架构写现状；工程规则写修改约束；schema/契约写精确格式；指南写作者操作；ADR 写重要决策原因；提案明确未实施。社区翻译沿用[现有维护政策](../../zh/translations.md)，核心文档只承担英/简中。

## 如何执行：按完成条件推进

下面是依赖顺序，不是发版日期，也不是已全部完成的清单。

| 阶段 | 可交付结果 | 完成条件 |
| --- | --- | --- |
| A：建立基线 | 核心/插件索引/内容维护者盘点格式和文档差异，选一个原创小冒险作为标准样例 | 同一份内容能验证、导入、开局、保存、重载；反例能复现既有阻断；支持的旧用户升级路径有验收 |
| B：跑稳完整流程 | 各功能 owner 优先处理导入、审阅、发布、取消、错误提示、模型兼容与并发 | 电脑/手机无需手改文件即可完成；取消保留草稿；旧请求/重复写入/越权被拦；私密信息不泄露 |
| C：作者可以独立创作 | 核心/插件索引/内容仓库共同提供版本匹配的英/简中快速入门、starter、验证结果、迁移说明 | 不改核心代码也能产出包；投稿/CLI/安装一致拒绝坏引用、runtime、路径；CI 验证实际产物 |
| D：接通冒险发现 | 冒险沿用内容市场分类，核心与 Hub 接入经审核的版本元数据 | 安装后能找到并选择包内冒险开局；扩权重新审核；安全更新保留旧局，不兼容明确解释 |
| E：扩展生态 | 加入 CoC/D&D 验收样例与一个专门的执行插件示例 | 外部作者能独立完成流程；停止维护可以标记/暂停，不转成核心的永久维护负担 |

**建议先做 A、B。** 第一份标准样例控制在两个场景、一个分支、一条私密线索、一本资料册、一张地图/图片，以及明确的 runtime 要求。用同一份产物完成验证、本地导入、导出重导入、开局、玩家可见性、存档重启、尝试不兼容更新。若声明确定性遭遇，就实际走规则 runtime；纯叙事示例如实写 reference/guided。

本地实现已提供原创的[灯火港湾作者示例](../../../plugins/examples/starter-adventure/README_zh-CN.md)。
[对应验收](../../../tests/test_starter_adventure_conformance.py)覆盖源目录与成品校验、安装、建局、
秘密投影、存档重载、导出再导入和存档引用阻断；负例覆盖执行入口、越界路径、缺失运行时、
非法世界关系和语言覆盖机制。它是包含关系地图的引导式示例，不是确定性战斗认证。
C–E 中的市场准入、发布证据与外部作者里程碑仍是独立阶段。

作者现有命令，从对应版本的核心仓库运行：

```bash
python scripts/validate_content_module.py path/to/my-content-pack --json
python scripts/package_plugin.py path/to/my-content-pack
```

前者复用安装的深度校验，阻断错误返回非零；后者验证宿主外壳并打包，**打包成功不等于已通过深度模块校验或游玩验收**。执行插件/主题使用相应宿主/SDK 检查。CI 还应验证生成后的真实包，才能把报告与该产物 digest 关联。

每个实施改动写清：观察到的问题、所属模块、受影响契约、实现、行为证据、文档与失败/恢复方式。能独立验收和回退的工作分开；必要的迁移与契约改动保持完整。不要一次创建万能 manifest，也不要为市场新政策自动破坏旧本地包。

衡量的是作者流程完成率、错误可理解性、恢复成功、越权/过期写入拒绝、引用保留、实际测试的模型兼容和费用可见性。先记录基线，再给对应阶段定目标；徽章应写测试版本和范围。长期积累的标准样例、兼容作品与可靠战役，才会形成可验证的优势。

## 当前契约的验收底线

内容身份不跟标题/语言漂移；服务端落实权限和模式限制；模型输出不绕过领域服务；旧用户数据不被系统模板覆盖；升级失败可解释且可恢复；移动端主流程可完成；扩展走 capability/adapter/registry。以上来自现行工程要求，不因本提案尚未采纳而放宽。

对于模块划分，权限与事务/回滚正确性属于核心承诺；经济玩法本身可以选择。不能仅凭删模块后多少测试失败就决定内核归属。拆分 `table_settings` 应说明持久化 slot 与旧值迁移，而不是把它们搬进另一处大杂烩。
