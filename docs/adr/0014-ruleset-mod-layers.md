# ADR-0014: 规则模组分发与扩展能力边界

- Status: Proposed
- Date: 2026-11-08
- Last revised: 2026-11-11

> 本次是本地提案修订，未表示上游已采纳或实现。2026-11-08 的初稿与公开 Issue #710 含有“先将 FU 并入 main”的路径；该路径不再是本地修订方案。公开 Issue 未随本次文件修改而更新。

## Context

社区 FU 分支表明，深度规则作者需要扩展检定、冲突流程、角色成长、特殊资源与界面。现有 content-pack 可以分发规则资料和内容，现有工具插件可以运行受管理进程；这两点并不等于外部规则运行时已经可以安装即用。

2026-11-11 的核验基线：

- 主仓 main：`9ab8389c61c0e5565a5d91db56e1304ceeac2497`；相对原施工计划的 `c6df281b96dc5fe9c38db90c12afd659a0e514a2`，仅 `RELEASE_NOTES.md` 与 `src/version.py` 改变。
- 索引仓 main：`104b3c2d3ad4531fd1074463442f4d114ce103e4`。
- `src/rulesets/builtin.py` 注册 Legacy 与 D&D 2024；不能由存在 CoC 规则模板推断存在同型的独立 CoC runtime。
- `RulesetRuntime` 的多种方法仍接收 `instance`、`rule`、`rng` 对象。内部 Protocol 是现有接缝，不是已发布的跨进程 ABI。
- 现有插件通过子进程/stdio RPC 运行；受管理进程提供生命周期和故障隔离，不能称为已经实现的操作系统沙箱。
- FU 提交目录含运行配置、凭据文件和数据库。本文只引用能力需求，不将该目录作为可公开的测试包。

本提案遵循 [ADR-0005](0005-composable-game-platform.md)、[ADR-0011](0011-application-actions-and-agent-delegation.md)、[ADR-0013](0013-gameplay-packages.md) 与工程规则。规则、玩法、内容、UI、工程代理保持独立职责。

## Decision

以下均为提议采用的方向；具体 schema、方法签名和执行隔离方式须经实验与契约评审确定。

### 1. 一个交付单位，多个能力贡献

继续使用 `.dfplugin`，沿用 `PluginHost` 的安装与生命周期边界。规则、内容、玩法、UI、文档和工具可以属于同一包，分别交给对应 owner 校验和注册，统一计算实际权限与风险。

保留旧 `plugin_type` 和 `contributes` 的解释。是否新增 schema 版本、字段命名空间或 plugin type 尚未定稿；不能预先把 `plugin_type: ruleset` 当作可用契约。纯内容不会因复合包装而获得执行权限。

规则兼容标签、硬依赖与运行时绑定分别处理：`compatible_rulesets` 是筛选标签，不能作为依赖满足的证据。

### 2. FU 保持为外部需求样本

不将 FU Fork 或 FU 专属共享路径并入 main 作为平台前置步骤。先制作可公开、权利清楚的最小外部测试扩展，验证建卡、动作、结算、多人投影、保存与恢复；再以 FU 级复杂度检验接口覆盖面。

只把被实际样例证明需要的通用接缝加入核心。FU 自定义步骤制、商人等 house rules 与“是否忠实实现原版 FU”分开验收，不能为达到原版规则一致性而擅改作者玩法。

### 3. 从真实契约提炼 SDK，不先承诺固定数量的钩子

骰制、检定、成长、恢复、冲突与投影是需求分类，不是已经稳定的“6～8 个公共钩子”。逐项记录：现有 owner、输入、输出、状态读写、权限、失败语义和测试，复用已有 capability，避免重复建立一套规则引擎。

参数配置仅覆盖当前解释器能确定执行并校验的轴；不承诺用 JSON 表达任意回合结构或复杂规则。数据输入也须校验，不能标为“天然安全”。

### 4. 外部运行时的权威与事务边界

优先实验受管理的独立进程/IPC 适配器。主程序保留 actor 授权、并发版本、RNG 回执、持久化、事务提交与重复提交防护；外部 runtime 对自己声明的规则语义负责。

实验必须明确：

1. 输入是显式 DTO 与必要状态快照，不传活的 `GameInstance`、私有 service 或对象反向调用入口。
2. runtime 可提议修改自己拥有的版本化状态；涉及角色、经济、世界等其它 owner 的变化，必须通过正式 effect/领域契约，禁止任意路径补丁。
3. 宿主校验授权、归属、schema、资源不变量与提交前版本，不在核心重写一遍 FU 的全部规则逻辑。
4. 结算响应在单个 staged transaction 中校验并提交；跨 owner 失败不得部分生效。RNG 输入或骰点回执与动作 identity 绑定，恢复时不盲目重骰。
5. 进程超时、崩溃、重启、重复请求与响应迟到均有确定处理；IPC 不能阻塞事件循环或在持有游戏锁时形成反向调用死锁。
6. 仅授予结算必需的服务端私密状态；宿主在投影下发玩家 UI/代理前实施可见性检查，不能依靠前端隐藏或插件自报身份。

操作系统层的文件、网络、环境变量、凭据和子进程权限另行验证。若某部署环境只能提供受信任原生代码模式，应如实展示风险，不冒称沙箱；普通纯内容功能不依赖这一高级模式。

### 4a. 角色库建卡与游戏绑定必须分离

角色库新建角色可以选择独立的 `creation_rule_id`，不受当前已加入对局的 `game_rule_id` 锁定。角色卡草稿、角色库成品卡和游戏内权威角色实例是不同对象；成品卡保留自身规则/runtime/version/digest，加入对局时再由服务端做兼容检查。复制或转换必须显式、可预览并重新通过目标规则验证，不能静默改写规则身份。

### 4b. 顺序检定与组合动作是规则能力，不是通用放行

规则 runtime 可以声明 `sequential_checks` 或 `composite_action`。步骤计划包含 actor、canonical ability、目标、依赖、顺序、资源、失败分支和结果状态；服务端负责骰子、次数、冷却、阶段、预算、幂等和 staged transaction。前置失败默认停止依赖步骤，旧规则继续保持每轮一个主检定。UI、AI GM、玩家与 DFAgent 只能提交同一正式动作计划，不能通过循环调用旧单检定接口绕过限制。

### 5. UI 分级扩展

- 第一阶段使用受限、版本化的声明式 UI，绑定当前 viewer 的服务端投影与正式动作。
- 高级阶段可提供预构建的隔离 HTML/CSS/JS 与消息桥。禁止的是第三方脚本进入宿主高权限上下文，不是禁止一切前端代码交付。
- 完整玩法视图按玩法绑定选择，未知玩法或必需 UI 不可用时进入可恢复的只读/管理页。
- 高级 UI 的 origin、sandbox、CSP、cookie、消息身份与服务端再鉴权需实际浏览器验证；路径不同不构成执行源隔离。

具体插槽、组件、SDK 版本和桥接协议均未在本 ADR 中冻结。

### 6. 分发、版本与存档

商店先支持现有包的确定来源：作者 Release 工件或明确的旧源码快照适配，索引记录批准版本与完整性身份。安装失败不得自动替换为 latest 或换源绕过暂停状态。

完整复合包依赖图不是静态商店 MVP 的前置。新能力在正式启用前，必须具有安装来源、能力版本和游戏绑定保护。运行中的局与暂停/结束/未成功加载但仍有 metadata 的存档都应纳入检查。

首版可在旧档绑定时阻止破坏性更新，不要求先实现所有版本并存。不能声称“沿用 runtime 字段，因此不影响持久化”；新增包身份/摘要/锁字段时须评估实际 schema、旧读者与迁移边界。

### 7. 验证顺序

1. 复核基线和旧生态回归，同时开始 runtime 事务实验与 UI 边界实验。
2. 交付现有插件/内容包的静态商店：固定审核工件、图片与详情、缓存、统一发现入口。
3. 打通最小外部 runtime 与声明式 UI，按实验结果稳定贡献与绑定契约。
4. Creator 工程服务和 DFAgent 内容制作可基于已有导出器推进；build 工具只有在真实构建服务存在后才注册。
5. 扩展到高级 UI、独立 gameplay 与受控开发 worker，最后用 FU 级样例做完整验收。

官方 runtime 可逐步验证 SDK 的表达能力；不要求先把全部内置实现改为跨进程模式才允许外部实验。

## Alternatives Considered

| 方案 | 取舍 |
|---|---|
| 先把 FU Fork 合并 main，再拆回第三方包 | 容易把样例的特例固化为平台接口；不采用为前置路径 |
| 任意文件替换或共享源代码补丁 | 冲突、升级、权限和回滚无法形成可靠契约；不采用 |
| 默认在核心进程 import 第三方代码 | 可直接接触宿主内存，失去预期的故障与权限边界；不采用默认方案 |
| 只开放声明式参数，不支持外部 runtime | 可覆盖普通变体，无法承担全部深度规则目标；不是最终范围 |
| 发布前先建完整万能 SDK、IDE 与依赖求解器 | 首次可验证交付过晚；改为样例驱动的阶段交付 |

## Consequences

### Benefits

- 作者通过独立包扩展，平台维护公共边界，不为每个规则增加专属分支。
- 普通作者继续使用低门槛内容路径，静态商店无需官方动态服务。
- UI、Agent 与玩家动作抵达同一领域逻辑，各自授权范围清晰。

### Costs / Risks

- 跨进程状态、确定性、事务、超时与跨端隔离仍需实证，不能由内部 Protocol 的存在推断完成。
- 稳定 SDK 带来公共 API 兼容成本；只冻结已有消费方证明需要的部分。
- 不可信代码测试必须与有发布凭据的 CI 阶段分离；哈希固定不等于代码安全审计。

### Migration / Compatibility

- 本次仅改提案文档，不改变运行行为、manifest、API 或存档。
- 实施时按实际受影响的契约分别提供 adapter、迁移或显式拒绝；旧包行为保持或明确升级边界。
- 不能以关闭功能开关为由忽略已写入的新绑定，也不能回退到不检查批准工件的旧下载路径。

## Validation

- 静态商店：审核后附件替换、tag 漂移、错误 hash、暂停 listing、离线和镜像回退均不能改变批准身份。
- 最小外部 runtime：角色创建、确定性动作、跨 owner 失败回滚、重复请求、并发冲突、超时、保存重启、多人投影。
- U1：不重编主前端即可增加角色卡/动作面板；动作仍服务端鉴权。
- 高级 UI：无法直接读取宿主 token、GM 私密投影或调用未授权 API；握手失败可恢复。
- 生命周期：安装中断、重启、卸载与旧存档绑定保护；旧插件、导出器和规则行为回归。
- 截至本次修订，当前工作区四组 runtime/event/architecture 测试 38 项通过；这不是外部 runtime 或整个平台的验收结果。
